# Встроенные двоичные файлы: происхождение и аудит

VD Google обещает, что внутри него не поставляется ничего непрозрачного. Он работает от
имени root и читает ваше самое приватное состояние, поэтому вы должны иметь возможность
точно видеть, что он в себе несёт. Эта страница перечисляет единственный нативный
инструмент, который поставляют приложение и модуль, откуда он берётся и как его проверить.

## Принцип

VD Google несёт ровно один нативный инструмент: команду `sqlite3` вместе с небольшим
набором разделяемых библиотек, которые ей нужны. Он требуется потому, что собственный
системный SQLite Android не может открыть базы данных других приложений на некоторых
прошивках производителей, из-за чего VD Google на таких устройствах ничего бы не прочитал.
См. [Архитектуру](ARCHITECTURE.md) о причинах.

- **Взято из апстрима, никогда с устройства.** `sqlite3` и его библиотеки берутся из
  официального репозитория пакетов **Termux** (`packages.termux.dev/apt`), из подписанных
  пакетов `.deb`, а не копируются из Termux, установленного на каком-то телефоне.
- **Одни и те же байты везде.** Идентичные файлы поставляются в приложении (под
  `assets/bin/`) и в модуле WebUI (под `bin/`), поэтому оба читают одним движком и
  согласуются.
- **Контрольная сумма - это личность.** По какому бы пути ни лежала копия, она является
  настоящим инструментом, только если её SHA-256 совпадает с записанным значением.
- **Записанный аудиторский след.** Каждый каталог ABI несёт `PROVENANCE.json`, в котором
  перечислены каждый исходный пакет (имя, версия, URL, SHA-256 файла `.deb`) и SHA-256
  каждого поставляемого файла. Ничего не включается без записи, которую вы можете проверить.

## Происхождение

`.github/scripts/build_bin.sh` собирает полезную нагрузку во время сборки, без компилятора
и без NDK. Для каждого ABI он:

1. читает индекс Termux Packages и разрешает пакет `sqlite` плюс его транзитивные
   зависимости (`readline`, `ncurses`, `zlib`, `libandroid-support`);
2. скачивает и распаковывает официальные подписанные файлы `.deb`;
3. копирует `sqlite3`, затем копирует только то замыкание разделяемых библиотек, которое
   двоичному файлу действительно нужно (разрешённое с помощью `readelf`), пропуская
   библиотеки, которые Android всегда предоставляет сам;
4. записывает `PROVENANCE.json`.

Двоичные файлы Termux динамически линкуются с собственными библиотеками Termux, поэтому
VD Google поставляет это замыкание рядом с `sqlite3` и запускает его с `LD_LIBRARY_PATH`,
указывающим на встроенный каталог `lib/`. Termux использует версионированные soname
(`libz.so.1`, `libreadline.so.8`, `libncursesw.so.6`), поэтому они никогда не конфликтуют
с собственными библиотеками фреймворка Android. `LD_LIBRARY_PATH` устанавливается только
для процесса `sqlite3`, никогда глобально.

## Файлы

Апстримная оболочка командной строки **SQLite**, пакет Termux **sqlite 3.54.1-1**. Одна
полезная нагрузка на ABI: двоичный файл `sqlite3` плюс его замыкание из четырёх библиотек
(`libreadline.so.8`, `libncursesw.so.6`, `libz.so.1`, `libandroid-support.so`). Каждый

рядом с двоичным файлом.

## Проверьте сами

Из клонированного исходного кода подтвердите каждый поставляемый файл:

```sh
sha256sum VDGoogle/app/src/main/assets/bin/*/sqlite3 VDGoogle/app/src/main/assets/bin/*/lib/* \
          VDGoogle/webui/bin/*/sqlite3 VDGoogle/webui/bin/*/lib/*
```

Каждый хеш должен совпасть со списком выше, а копии приложения и WebUI должны совпадать
друг с другом. Чтобы проверить всю полезную нагрузку от начала до конца, заново скачайте
закреплённые URL файлов `.deb`, перечисленные в каждом `PROVENANCE.json`, распакуйте их и
сравните значения SHA-256 файлов.

## Для чего он используется

`sqlite3` запускается от имени root против копии базы, отложенной в сторону, исключительно
для **чтения**. Он никогда не используется для записи в какие-либо базы данных Google.
Его единственная задача - позволить VD Google читать одни и те же значения на каждом
устройстве. Никакой другой нативный двоичный файл не поставляется.
